# M6 — GitHub: conexión y Pull Requests — Plan de implementación

> **Para agentes:** SUB-SKILL OBLIGATORIA: usar superpowers:subagent-driven-development (recomendado) o superpowers:executing-plans para ejecutar este plan tarea por tarea. Los pasos usan casillas `- [ ]`.

**Meta:** pestaña GitHub por proyecto: conectar con PAT (cifrado con `safeStorage`), listar y crear Pull Requests de los repos con remote `github.com`.

**Arquitectura:** migración 10 con `integrations`; secreto en archivo cifrado fuera de SQLite; cliente `fetch` + Zod como único punto de red en main; dos servicios (integración y PRs) detrás de 8 canales IPC con nombre; UI nueva en `features/github/`.

**Stack:** Electron `safeStorage`, `fetch` nativo, Zod, `node:sqlite`, React + Zustand (ya existentes). Sin dependencias nuevas.

**Spec:** [docs/superpowers/specs/2026-10-23-m6-github-design.md](../specs/2026-10-23-m6-github-design.md)

## Reglas del proyecto que sustituyen al flujo TDD

CLAUDE.md prohíbe tests automatizados (ni crearlos, ni ejecutarlos, ni proponerlos). Por eso **no hay pasos de test**: cada tarea termina con `npm run check` (debe quedar verde) y una **prueba manual** que hace el usuario. Tampoco hay pasos de commit: se commitea solo cuando el usuario lo pida (Conventional Commits, con CHANGELOG actualizado en ese mismo commit). Tras cada tarea: `graphify update .`.

- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`; sin canal genérico `invoke(channel, payload)`.
- Procesos hijos solo por `src/main/exec/run.ts` (ejecutable + array, nunca `shell: true`).
- Token solo en main; nunca en SQLite, logs, `executions`, estado del renderer ni respuestas IPC.
- Todo texto de error o log pasa por `redactSecrets()` ([git-errors.ts](../../../src/main/services/git-errors.ts)); ya cubre `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_` y `github_pat_`.
- Migraciones solo hacia adelante: añadir `m010` en [migrations/index.ts](../../../src/main/db/migrations/index.ts) y a `MIGRATIONS`.
- Añadir una capacidad = canal en `src/shared/types/ipc.ts` + handler en `src/main/ipc/handlers.ts` + binding en `src/preload/index.ts` + schema. `assertChannelCoverage` aborta el arranque si falta alguno.
- `import { type X }` para tipos; TypeScript estricto (`noUncheckedIndexedAccess`); sin `eslint-disable` ni `@ts-ignore` sin razón escrita.
- Comentarios solo para el porqué no obvio; seguir el estilo del código vecino. Respuestas y textos de UI: el código existente está en inglés, mantener inglés en UI y comentarios.

## Review Focus

Fallos que el spec implica y que ninguna prueba manual del spec cubre; cada uno tiene su paso de verificación en la tarea indicada.

1. Proyecto borrado con GitHub conectado: la fila cae por `ON DELETE CASCADE` pero el archivo `userData/secrets/<id>.bin` quedaría huérfano con el token (Tarea 3).
2. `repositoryId` que pertenece a otro proyecto: el servicio debe rechazarlo, no usar el token del proyecto A contra el repo del B (Tarea 4).
3. `restoreDefaultTabs` / `reorder` con la pestaña `github` presente: no debe borrarla ni rechazar el orden (Tarea 3).
4. Remote con credenciales incrustadas (`https://user:tok@github.com/o/r.git`) o con host parecido (`github.com.evil.io`, `https://github.com@evil.io/…`): el parser acepta lo primero sin filtrar el token y rechaza lo segundo (Tarea 2); `openUrl` rechaza hosts engañosos (Tarea 4).
5. Respuesta de GitHub con forma inesperada o `null` en campos (autor borrado = `user: null`; PR de fork con `head.repo: null`): no debe romper la lista (Tarea 2).

## Decisión a confirmar

El spec dice "contexto API" para el registro en `executions`, pero la tabla tiene `CHECK (context IN ('local','remote'))` y reconstruirla es una migración arriesgada. Este plan usa `context = 'remote'`, `kind = 'github_create_pr'`, `ssh_host_id = NULL` y `repository_id = NULL` (el repo va en `args`) para que la pestaña Git no muestre estas filas en su historial. Si prefieres un valor `api`, hay que reconstruir `executions` y es otra tarea.

### Tarea 2: Cliente de API y parser de remote

**Archivos:**
- Crear: `src/main/services/github-api.ts`, `src/main/services/github-remote.ts`, `src/shared/schemas/github.ts`

**Interfaces:**
- Consume: `redactSecrets` ([git-errors.ts](../../../src/main/services/git-errors.ts)), `StewardServiceError`.
- Produce (`github.ts`, solo los schemas que esta tarea necesita; la Tarea 3 y 4 añaden los suyos al mismo archivo):
  - `githubPullSchema`: `{ number: int, title: string, author: string | null, headRef: string, baseRef: string, draft: boolean, state: 'open' | 'closed' | 'merged', url: string, createdAt: iso, updatedAt: iso }`; tipo `GithubPull`.
  - `githubPullPageSchema`: `{ items: GithubPull[], page: int, hasNext: boolean }`; tipo `GithubPullPage`.
  - `githubPullStateSchema = z.enum(['open','closed','all'])`.
- Produce (`github-remote.ts`): `parseGithubRemote(url: string | null): { owner: string; name: string } | null`.
- Produce (`github-api.ts`): `createGithubApi(deps?: { fetchImpl?: typeof fetch }): GithubApi` con
  - `getUser(token: string): Promise<{ login: string; scopes: string[] }>`
  - `getRepo(token: string, owner: string, name: string): Promise<{ defaultBranch: string }>`
  - `listBranches(token, owner, name): Promise<string[]>` (hasta 100, ordenadas)
  - `listPulls(token, owner, name, query: { state: GithubPullState; page: number }): Promise<GithubPullPage>`
  - `createPull(token, owner, name, body: { base: string; head: string; title: string; body: string; draft: boolean }): Promise<{ number: number; url: string }>`

- [ ] **Paso 1:** `parseGithubRemote`: acepta `https://github.com/o/r`, `…/r.git`, con barra final, con credenciales incrustadas (se ignoran, nunca se devuelven), `git@github.com:o/r.git` y `ssh://git@github.com/o/r.git`. Rechaza (`null`) cualquier otro host, incluidos `github.com.evil.io` y `https://github.com@evil.io/…`; `owner`/`name` deben cumplir `/^[A-Za-z0-9_.-]+$/` y no ser `.` ni `..`. Parsear con `new URL` para https/ssh y con regex anclada para el formato scp.
- [ ] **Paso 2:** `github-api.ts` — petición común: base `https://api.github.com` fija (constante, no configurable), cabeceras `Authorization: Bearer <token>`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, `User-Agent: Steward`; `AbortController` con 15 s; `owner`/`name` se pasan por `encodeURIComponent`.
- [ ] **Paso 3:** mapeo de errores (todos `StewardServiceError`, mensajes pasados por `redactSecrets`): 401 → `GITHUB_AUTH_FAILED`; 403 con `x-ratelimit-remaining: 0` → `GITHUB_RATE_LIMITED` con el reset formateado en `details`; otros 403 → `GITHUB_AUTH_FAILED` con "token sin permisos suficientes"; 404 → `GITHUB_NOT_FOUND` ("no existe o el token no tiene acceso"); 422 en `createPull` → `GITHUB_FAILED` con el primer `errors[].message` de GitHub (p. ej. "A pull request already exists"); `fetch` lanza o aborta → `GITHUB_UNREACHABLE`; respuesta que no valida con Zod → `GITHUB_FAILED` genérico, y el detalle solo a `console.error` ya redactado.
- [ ] **Paso 4:** schemas Zod internos de respuesta, tolerantes a nulos: autor `user: null` → `author: null`; `merged_at` no nulo → `state: 'merged'`; `head.repo` puede ser `null` (se usa solo `head.ref`). `hasNext` sale de la cabecera `Link` con `rel="next"`. `getUser` lee scopes de `x-oauth-scopes` (cabecera ausente en fine-grained → `[]`).
- [ ] **Paso 5:** `npm run check`. Esperado: sin errores.
- [ ] **Prueba manual:** ninguna aún (no hay UI); se ejercita en la Tarea 3.
