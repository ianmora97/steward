# M6.5 — GitHub Actions: workflows, runs y logs — Plan de implementación

> **Para agentes:** SUB-SKILL OBLIGATORIA: usar superpowers:subagent-driven-development (recomendado) o superpowers:executing-plans para ejecutar este plan tarea por tarea. Los pasos usan casillas `- [ ]`.

**Meta:** sub-vista **Actions** dentro de la pestaña GitHub: workflows, runs con estado y conclusión, jobs/steps por run y log de un job, todo de solo lectura.

**Arquitectura:** cuatro métodos nuevos en el cliente `fetch` + Zod de M6; un servicio de solo lectura que reutiliza `withToken` y la resolución de repo; cinco canales IPC; el estado operativo (`healthy | degraded | failing | unknown`) se calcula en main a partir de los últimos 30 runs y no se guarda. Sin migración.

**Stack:** el de M6 (Electron, `fetch`, Zod, React + Zustand). Sin dependencias nuevas.

**Spec:** [docs/superpowers/specs/2026-10-23-m6-5-actions-design.md](../specs/2026-10-23-m6-5-actions-design.md). Parte de [M6](2026-10-23-m6-github.md), ya implementado en `milestone-6-github` (esta rama, `milestone-6-5-actions`, está apilada sobre ella).

## Restricciones globales

- Solo lectura: no escribir en `executions`, SQLite ni disco (salvo lo ya existente). Sin migración nueva.
- Token solo en main; todo texto que salga de main hacia el renderer pasa por `redactSecrets()` ([git-errors.ts](../../../src/main/services/git-errors.ts)).
- Sin canal genérico: añadir una capacidad = canal en `src/shared/types/ipc.ts` + handler en `src/main/ipc/handlers.ts` + binding en `src/preload/index.ts` + schema en `src/shared/schemas/github.ts`. `assertChannelCoverage` aborta el arranque si falta alguno.
- owner/repo siempre salen del remote guardado del `repositoryId`, que debe pertenecer al `projectId`; `runId`/`jobId`/`workflowId` son enteros ≥ 1 validados y van en la ruta con `encodeURIComponent`.
- Los logs se pintan como texto, nunca como HTML. Tope de descarga 20 MB, tope de salida 200 KB (valores del spec).
- `import { type X }`; TypeScript estricto (`noUncheckedIndexedAccess`); sin `eslint-disable` ni `@ts-ignore` sin razón escrita. Para quitar secuencias ANSI no usar un literal de regex con caracteres de control: construirlo con `new RegExp(String.fromCharCode(27) + …)` (la regla `no-control-regex` está activa).
- Comentarios solo para el porqué no obvio; UI y comentarios en inglés, como el código existente.

## Review Focus

Fallos que el spec implica y que ninguna prueba manual del spec cubre; cada uno tiene su verificación en la tarea indicada.

1. Runs con campos nulos (`actor`, `head_branch`, `run_started_at` en runs en cola, runs de bots): la lista no debe romperse (Tarea 1 schemas, Tarea 3 UI).
2. Valores de `status`/`conclusion` que Steward no conoce (`waiting`, `requested`, `pending`, `stale`, `action_required`): chip genérico, sin excepción y sin contar como éxito ni fallo en la salud (Tareas 1 y 3).
3. Repositorio con Actions desactivado o sin workflows/runs: estado vacío, no error (Tarea 3).
4. Cambiar rápido de repo, de workflow o de vista (PRs ↔ Actions) con peticiones en vuelo: una respuesta tardía no debe pisar la vista nueva (Tarea 3).
5. Log con `\r`, secuencias ANSI, líneas larguísimas o UTF-8 cortado en el límite de los 200 KB: el texto sale limpio, sin colores ni caracteres de control, y el recorte empieza en una línea completa (Tareas 1 y 2).

### Tarea 1: Schemas, cliente de API y utilidades puras

**Archivos:**
- Modificar: `src/shared/schemas/github.ts`, `src/main/services/github-api.ts`
- Crear: `src/main/services/github-health.ts`, `src/main/services/github-log.ts`

**Interfaces:**
- Consume: `request()` y los helpers `parseBody`, `mapStatus`, `repoPath` de `github-api.ts`; `redactSecrets`.
- Produce (schemas, con su tipo `z.infer` exportado):
  - `githubWorkflowSchema`: `{ id: int, name: string, path: string, state: string }` → `GithubWorkflow`.
  - `githubRunSchema`: `{ id: int, runNumber: int, title: string, workflowId: int, workflowName: string, status: string, conclusion: string | null, event: string, branch: string | null, sha: string, actor: string | null, url: string, createdAt, startedAt: string | null, updatedAt }` → `GithubRun`. `status` y `conclusion` son `string` y no enum: GitHub añade valores.
  - `githubRunPageSchema`: `{ items: GithubRun[], page: int ≥ 1, hasNext: boolean }` → `GithubRunPage`.
  - `githubStepSchema`: `{ number: int, name: string, status: string, conclusion: string | null }`; `githubJobSchema`: `{ id: int, name: string, status: string, conclusion: string | null, startedAt: string | null, completedAt: string | null, url: string, steps: GithubStep[] }` → `GithubJob`.
  - `githubJobLogSchema`: `{ text: string, truncated: boolean, tooLarge: boolean }` → `GithubJobLog`.
  - `githubHealthSchema`: `{ status: 'unknown' | 'healthy' | 'degraded' | 'failing', basedOnRuns: int, failingWorkflows: string[] }` → `GithubHealth`.
  - Entradas: `githubRepositoryInputSchema` `{ projectId, repositoryId }` (para `listWorkflows` y `getHealth`); `githubListRunsInputSchema` `{ projectId, repositoryId, workflowId: int ≥ 1 | null (default null), page: int 1–1000 (default 1) }` con tipo de entrada `GithubListRunsInput = z.input<…>`; `githubListJobsInputSchema` `{ projectId, repositoryId, runId: int ≥ 1 }`; `githubGetJobLogInputSchema` `{ projectId, repositoryId, jobId: int ≥ 1 }`. Todos con tipo `…Input`.
- Produce (API), añadidos a `interface GithubApi`:
  - `listWorkflows(token, owner, name): Promise<GithubWorkflow[]>`
  - `listRuns(token, owner, name, query: { workflowId: number | null; page: number }): Promise<GithubRunPage>`
  - `listJobs(token, owner, name, runId: number): Promise<GithubJob[]>`
  - `getJobLog(token, owner, name, jobId: number): Promise<GithubJobLog>` (texto **crudo**, sin limpiar)
- Produce (puras): `computeHealth(runs: GithubRun[]): GithubHealth` en `github-health.ts`; `cleanLog(text: string): string` en `github-log.ts`.

- [ ] **Paso 1:** añadir los schemas anteriores a `src/shared/schemas/github.ts` (mismo estilo que los de PRs; `isoTimestampSchema` para fechas obligatorias, `.nullable()` para las opcionales).
- [ ] **Paso 2:** `github-api.ts` — `listWorkflows`: `GET {repoPath}/actions/workflows?per_page=100`; respuesta `{ workflows: [...] }` validada con Zod y mapeada a `GithubWorkflow`.
- [ ] **Paso 3:** `listRuns`: ruta `{repoPath}/actions/runs` o `{repoPath}/actions/workflows/{workflowId}/runs` si `workflowId !== null`; query `per_page=30&page=N`; respuesta `{ workflow_runs: [...] }`. Mapeo tolerante a nulos igual que `listPulls`: `actor` = `actor?.login ?? null`, `title` = `display_title` (si falta, `name`), `workflowName` = `name ?? ''`, `branch` = `head_branch ?? null`, `startedAt` = `run_started_at ?? null`, `sha` = `head_sha`, `url` = `html_url`. `hasNext` con la misma regex de `Link` que `listPulls` (extraerla a una función `hasNextPage(headers)` compartida).
- [ ] **Paso 4:** `listJobs`: `GET {repoPath}/actions/runs/{runId}/jobs?per_page=100`; respuesta `{ jobs: [...] }` con `steps` opcional (`?? []`); `startedAt`/`completedAt` nullables.
- [ ] **Paso 5:** `getJobLog`: `request()` hoy lee siempre JSON y falla con texto. Refactorizar la parte común (fetch con timeout y señal, mapeo de errores por `mapStatus`) a un helper interno que devuelva el `Response` ya validado como `ok`, y que `request` y `getJobLog` usen. En `getJobLog`, leer `response.body` con `getReader()`, acumulando `Uint8Array` hasta **20 MB** (`MAX_LOG_DOWNLOAD_BYTES`): al pasarse, `reader.cancel()` y devolver `{ text: '', truncated: true, tooLarge: true }`. Si no, conservar los **últimos 200 KB** (`MAX_LOG_TAIL_BYTES = 200 * 1024`) decodificados con `TextDecoder('utf-8')`; si hubo recorte, descartar el primer fragmento hasta el primer `\n` para empezar en línea completa y devolver `truncated: true`. El cuerpo vacío devuelve `text: ''`. El timeout de 15 s cubre solo la cabecera y la descarga (limpiar el timer al terminar de leer).
- [ ] **Paso 6:** `github-health.ts`: `computeHealth` según el spec. Conclusiones de fallo: `failure`, `timed_out`, `startup_failure`; de éxito: `success`; solo cuentan runs con `status === 'completed'` y conclusión en uno de esos dos conjuntos (el resto se ignora). "Último" = primero de la lista (GitHub devuelve los más recientes primero). `failingWorkflows` = nombres (únicos, en orden de aparición) de los workflows cuyo último run contado falló; `basedOnRuns` = `runs.length`.
- [ ] **Paso 7:** `github-log.ts`: `cleanLog` normaliza `\r\n` a `\n`, descarta el tramo anterior a un `\r` suelto dentro de cada línea (barras de progreso), elimina secuencias ANSI (CSI `ESC [ … letra`) y cualquier otro carácter de control salvo `\n` y `\t`, y pasa el resultado por `redactSecrets`. Construir las regex con `String.fromCharCode` (ver Restricciones globales).
- [ ] **Paso 8:** `npm run check`. Esperado: sin errores.
- [ ] **Prueba manual:** ninguna aún (sin UI); se ejercita en las Tareas 2 y 3.

- [ ] **Paso 9:** `npm run check`. Esperado: sin errores.
- [ ] **Prueba manual (usuario):**

  2. Filtrar por workflow cambia la lista; *Load more* solo aparece con más de 30.
  3. Desplegar un run: jobs y steps con su conclusión; *View log* muestra texto sin colores ni secretos y avisa si se truncó.

  5. Repo sin runs o sin workflows → mensaje vacío; repo sin remote GitHub → "not on GitHub".
  6. Token sin permiso de Actions → 403 con la pista; token revocado → pide reconectar.
  7. Log de un run de más de 90 días o inexistente → "log not available".
  8. Cambiar rápido de repo, de workflow y entre *Pull requests* y *Actions*: nunca queda en pantalla la lista de otro repo ni de otro filtro.
