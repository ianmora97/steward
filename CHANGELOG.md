# Changelog

All notable changes to Steward are recorded here, newest first, and double as the source for release notes.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); entries are tagged with the milestone they belong to.

Categories: **Added** · **Changed** · **Fixed** · **Removed** · **Security** · **Docs** · **Tooling**.

> Maintenance rule: every commit that changes behaviour, tooling or docs adds a line here, under `Unreleased`.
> When a release is cut, `Unreleased` is renamed to the version and date, and a new empty `Unreleased` is opened.

## [Unreleased]

### Added
- **M13** **Domains in the VPC tab**: the VPC tab is one view for servers, domains and their monitoring. Each environment (Production, Staging…) shows its servers as cards, and inside each card the domains that server answers for, with three lights (DNS, certificate, web page), the days left on the certificate, the response time and whether the domain is healthy. A domain belongs to a server: you pick it when adding the domain, or add it straight from the server's card with **+**. Domains served from elsewhere (a CDN, a static site, another provider) get a *Without a server* card in their environment. *Check all* now also runs the domains' checks, and the fleet panel counts healthy, degraded, failing and unchecked domains. The name is cleaned up for you (lowercase, trailing dot removed, international names converted) and anything that is not a plain domain name, such as a URL with a path, a port or an IP address, is refused with a message that says what to type. Removing a domain asks for confirmation and deletes its checks and history; nothing is ever changed on the domain itself.
- **M13** **Checks**: a new domain comes with three recommended checks (switch them off in the dialog if you prefer): its DNS every 5 minutes, its certificate every hour and its HTTPS page every minute. Each domain row shows whether it is *Healthy*, *Degraded* or *Failing* (from the latest results), the days left on its certificate, the last response time, when it was last checked, and Cloudflare, CloudFront or an AWS load balancer when the response comes through one. A certificate that is expired, for another name, self-signed or about to expire makes the domain *Failing* right away. DNS can compare what a domain resolves to against the addresses or CNAME you expect and report drift. HTTP follows up to five redirects, shows each hop and warns when one drops from HTTPS to plain HTTP. Checks run only while Steward is open (it is not a 24/7 monitor), never more than four at a time, at most 20 active per project, and keep a week of history. Nothing about the page is stored except the status, a few headers and whether the expected text was found.
- **M13** **Domain detail**: open a domain from its server's card to see one card per check with the latest result laid out for its kind (DNS records and drift; certificate holder, issuer, validity, names and chain; redirect chain, timing per phase, headers and whether the expected text was found), a response-time chart with failures marked, and a history. The domain itself is edited or removed from the same place. Each check can be run on the spot (*Run now*), switched off or on, edited or deleted, and new ones added for the DNS, the certificate (any port) or a page (scheme, path, GET or HEAD, accepted status range, text to find) with an interval from 30 seconds to a day.
- **M12** **Monitoring** tab (add it from the **+** on the tab bar): connect a project to Grafana with a read-only token and see its dashboards, folders and active alerts. Each source shows two badges, *Connected / Auth error / Unreachable* and *Healthy / Degraded / Failing*, plus the Grafana version, who the token belongs to and the round-trip time. *Test connection* works before saving.
- **M12** **Metrics**: add Prometheus (directly, or through a Grafana you already connected, so one token reaches everything), write PromQL with metric-name suggestions, pick 15 min to 7 days or an exact range, and read the result as a graph or a table. The step is chosen for you so a huge range never breaks the query; *Targets* shows what is up or down and *Alerts* what is firing or pending.
- **M12** **Logs**: add Loki (directly or through Grafana), build the selector from its labels, run LogQL over the last 15 minutes to 24 hours, and read the lines with colour by level, a histogram of lines over time, a filter, and the full line (JSON lines open as fields) with a copy button. **Live** follows new lines every two seconds without repeating or skipping any, and can be paused. Tokens and passwords that appear in a log are masked before they reach the screen.
- **M12** **Issues**: add a Sentry project (organization and project slugs, a token with `project:read`, `event:read` and `org:read`; sentry.io or your own server), search its issues with Sentry's syntax over 1 hour to 14 days and open one to see its latest event: message, release, tags and the stack trace with your own code highlighted. In Investigate, each recent deploy shows how many unresolved issues its release (named after the commit) has.
- **M12** **Services and signals**: describe each service of a project once (how to find it in Loki and Prometheus, its repository, the server and Docker container it runs on) and the signals worth watching for any of them (error rate, latency, CPU, memory and error-log rate to start, all editable) as queries with `{{matcher}}` and `{{selector}}` in place of the service's labels. A preview shows the exact query a service gets.
- **M12** **Investigate**: pick a service and a window (15 min, 1 h, 6 h, 24 h or *since the last deploy*) and see, on one page, a timeline of its deploys and alerts, a chart per signal with the deploys marked on it, the service's error log lines (the pattern is yours to change), whether its container is running, and a table with each signal's average before and after every deploy. If Loki is down the rest still shows, and the table says plainly that a difference is a lead, not proof of cause.
- **M12** Servers with their own certificate authority work by choosing its CA file; skipping certificate checks is possible but asks for confirmation and leaves a permanent warning on the source. Tokens are stored encrypted and never shown again; Steward only reads from these servers.

The icon shows on the environment list and as the header of each VPC group.

Check buttons show a spinner and *Checking…*.
- **M11.5** Git tells you what it did: a toast for *Committed …*, *Branch … created / deleted*, *Switched to …*, *Changes discarded*, *Merge aborted* and the first line of what a fetch, pull or push printed; *Pull request #N created* for GitHub. The long green banner is gone.

- **M11** VPC opens on a **Home**: every connection as a card grouped by environment, with whether it answered the last time it was checked, its last command, any open shell, *Check*, *Connect* and *Check all*. The old list-and-editor is the *Connections* sub-tab.
- **M11** Project **Settings** in four sections: *General* (name, description, colour and icon, archive and delete), *Services* (which tabs are on the bar, and their order), *Integrations* (connect, check and disconnect GitHub) and *Workspace* (repositories, default shell, environments, local storage). A project's colour and icon now show in the sidebar and on its card.
- **M11** A **+** on the tab bar adds a service (VPC, Deployments, Docker, MongoDB, Redis, each with a one-line description) and a **×** on a service takes it off the bar; nothing is deleted either way.
- **M11** Redis tab for every project, with four views: *Browser*, *Workbench*, *Pub/Sub* and *Insights*. Connect to a Redis on your machine, on your network or in the cloud: standalone, **Sentinel** or **Cluster**, with a password, an ACL user, a database number and TLS (CA, client certificate and key files, passphrase). *Test connection* tells you the version, deployment, role, latency and key count before you save, and a replica is treated as read-only.
- **M11** Key browser that never blocks the server: keys load a page at a time with `SCAN` (Steward never runs `KEYS`), filtered by pattern and type, as a **Tree** split by a delimiter of your choice (`:` by default) or a plain **List**. The tree says its counts are of the keys loaded so far, next to the server's total.
- **M11** Open any key to see its value and expiry: strings, hashes, lists, sets, sorted sets, streams (with consumer groups) and RedisJSON, always paged. Values show as text, JSON, hex or base64, and binary values open as hex; a string over 1 MB shows only its first megabyte. Measure a key's memory on demand.
- **M11** Create, edit and delete: set a string without losing its expiry, add / edit / remove hash fields, list items, set members, sorted-set scores and stream entries, set or remove an expiry, rename and delete keys. *Delete matching…* counts the keys first, deletes in batches and refuses if the count changed; the pattern `*` needs the connection's name typed.
- **M11** Workbench: a Redis console with history (up / down), command-name completion (Tab) and saved commands. Output looks like `redis-cli`. Commands that would stop the server, change replication, hold the shared connection (blocking commands, transactions, `SELECT`) or stream everything (`MONITOR`) are refused; `FLUSHDB`, `FLUSHALL`, `CONFIG SET`, `KEYS`, scripts and the like ask for confirmation first.
- **M11** Insights: a live dashboard (operations per second, memory, clients, hit rate, expired and evicted keys, replicas, persistence) with five minutes of history, the slow log (with reset), connected clients, the server configuration (passwords hidden) and a **memory analysis** that measures a sample of up to 5000 keys and groups them by prefix and type.
- **M11** Pub/Sub: subscribe to channels and patterns, watch messages arrive (last 1000 kept per subscription) and publish. Subscriptions end when you leave the tab.
- **M11** Connections can be tied to an environment, as in MongoDB. In a protected environment a connection starts **read-only**, and Steward refuses every write on a read-only connection itself (editing, deleting, publishing and console commands that write, decided by the server's own command flags). Every change is recorded in the activity history without the values.
- **M10** MongoDB tab for every project: connect to a MongoDB on your machine, on your network, by IP, or on Atlas (`mongodb+srv`), with or without authentication and TLS. Paste a connection string or fill in the fields (host, port, user, password, authentication database, replica set, read preference, CA and client certificate files). *Test connection* tells you the server version, latency and topology before you save.
- **M10** Browse databases and collections in a filterable tree, with sizes and per-collection statistics. Query with the filter bar in shell syntax (`{ age: { $gt: 30 }, _id: ObjectId("…") }`), with projection, sort, page size and a time limit; see the results as a **List**, as **JSON** or as a **Table**, 20–500 per page with the total count.
- **M10** Insert, edit, clone and delete documents. Editing keeps every BSON type of the fields you did not touch (ObjectId, dates, 64-bit integers, decimals, whole-number doubles…), and if someone changed the document on the server since you opened it, Steward says so before overwriting. *Delete matching…* and *Update matching…* show the real count first and refuse to run if it changed in between; an empty filter needs the collection name typed.
- **M10** Aggregations built stage by stage, with a preview of each stage (first 20 documents) and *Explain*; indexes (list with usage and size, create with unique / sparse / TTL / partial, drop); schema analysis from a random sample; validation rules; saved queries and pipelines; import and export as JSON, JSON Lines or CSV.
- **M10** Connections can be tied to an environment. In a protected environment a connection starts **read-only**, and Steward refuses every write on a read-only connection (insert, edit, delete, drop, index, import, `$out`/`$merge`) itself, not just by greying buttons. Dropping a collection or database needs its exact name typed, plus the connection's name on a protected one. Every change is recorded in the activity history without the document contents.
- **M8** Docker tab for every project, with four views: *Containers*, *Images*, *Volumes & networks* and *Compose*. Pick where it runs: this machine or any of the project's SSH servers. If Docker is not installed, not running, not allowed for your user or the server is unreachable, the tab says which and what to do instead of showing an error.
- **M8** Steward starts Docker for you. Opening the Docker tab with the daemon off launches Docker Desktop in the background (once per visit, on this machine only), shows *Starting Docker…* while it comes up and switches to the containers by itself. There is also a *Start Docker* button if you want to retry. A server's Docker is never started from Steward.
- **M8** Containers: filter by name, image or Compose project; state shown as a pill (running, exited, exited with error, unhealthy, paused…); CPU and memory refreshed every few seconds; start, stop, restart, unpause, kill and remove. Open a container for its details (ports, mounts, networks, environment, labels) and live logs with pause, filter and a 2000-line window.
- **M8** *Shell* on a running container opens in the Terminal tab (`docker exec -it`, using bash when the image has it), on this machine or on the server over SSH.
- **M8** Images: pull by name, remove, and see which containers use each one. *Prune* (stopped containers, dangling images, unused volumes or networks, or everything unused) shows `docker system df` before asking you to confirm.
- **M8** Compose: Steward finds `compose.yaml` / `docker-compose.yml` at the root of the project's repositories, shows each service's state and runs Up, Down, Restart, Stop and Pull. *Down + volumes* asks first because it deletes data.

- **M7** Deployments tab with three views: *Targets*, *History* and *Environments*. A project now has environments (Production, Staging…) you can create, reorder and delete; deleting is refused while targets or deployment history still depend on one.
- **M7** Protected environments: a deploy to one makes you type its name exactly before anything runs, and Steward checks it again itself. Production-like environments are protected automatically when your existing servers are migrated; removing the protection from an environment asks for confirmation.
- **M7** Deploy targets run a fixed command on one of your servers over SSH (with an optional directory and a timeout, 120 s by default) or start a GitHub Actions workflow you pick, on a branch or tag you choose. Targets that point at a server or repository you later delete are marked *Broken* and cannot be deployed until you fix them.
- **M7** When you deploy a workflow, Steward reads the workflow file and shows the inputs it asks for (text, number, checkbox, choice), with the workflow's own defaults. It refuses a workflow that cannot be started by hand and values the workflow does not accept.
- **M7** The deploy history shows what confirmed each result: *confirmed by exit code* for a command, *confirmed by GitHub* for a workflow. A command deploy shows its output; a workflow deploy shows its jobs, steps and logs. If a command times out, the connection drops while it runs, GitHub cannot confirm a dispatch, a run never appears or Steward is closed in the middle of a deploy, the result is *Unknown* and says what to check, never a guess. A workflow deploy still running when you close Steward is followed again when you reopen it.
- **M7** One deploy at a time per target, and every deploy is also recorded in the activity log.

Very large logs and logs GitHub has already deleted (after 90 days) say so instead of failing.
- **M6.5** Two separate signals at the top of Actions: *Connection* and *Workflows* (healthy, degraded, failing or unknown, from the latest 30 runs). A failing workflow shows as failing while the connection still reads connected. *Refresh* re-reads everything.

### Security
- **M12** Monitoring only reads: no channel changes anything on Grafana, Loki, Prometheus or Sentry. Addresses come from a saved source (http or https, no credentials in the URL), tokens live in the encrypted secret store and never reach the page, a redirect to another address is refused instead of followed (so a token is never sent elsewhere), answers are capped at 8 MB and every request times out, and log lines and error messages are scanned for tokens and passwords before they leave the main process.
- **M10** A connection string usually holds a password. It is stored encrypted with the OS keyring (`safeStorage`) under the connection id, never in the database, and it never comes back to the screen: editing a connection shows only the host. Certificate and key files are referenced by path and never read by Steward. Accepting invalid certificates is an explicit option and keeps a warning on the connection.
- **M10** Filters, documents and pipelines you type are parsed, never evaluated: a function call that is not a BSON constructor is refused. Error messages are redacted before they are shown.
- **M10** Importing works on a file you picked in a native dialog; the screen only holds an opaque token for it, never a path.
- **M8** A container's environment variables whose names look like secrets (`PASSWORD`, `TOKEN`, `KEY`, `SECRET`…) are shown without their value: the value never leaves the main process. Log lines are redacted for tokens and URL credentials before they reach the screen.
- **M8** Docker commands on a server are built from fixed templates with every value validated and quoted; a container or image name can never become shell syntax.
- **M6** The GitHub token is encrypted with the OS keyring (`safeStorage`) in a file under Steward's data folder, readable only by the main process. It is never stored in the database, logs, activity history or the UI, and it is not sent anywhere except `api.github.com`. If the system cannot encrypt secrets, Steward refuses to store the token.
- **M6** Links opened from Steward must be plain `https://github.com/…`; repository owner and name are taken from the stored remote, never from the UI.
- **M4** The renderer can only send keystrokes and resize requests to terminals that already exist; folder and shell are resolved in the main process, and there is still no channel that runs a command string. Terminal logs mask URL credentials and GitHub tokens.
- **M3** Commit hashes and file paths are validated in the schema before they reach `git`.
- **M2** Git runs with `GIT_TERMINAL_PROMPT=0`, `GIT_LITERAL_PATHSPECS=1` and `LC_ALL=C`; arguments are always arrays, so a branch or file named like shell syntax is plain data.
- **M2** Destructive actions (discard, force-delete a branch) require `confirmed: true` in the IPC schema, and the UI states what will be lost first.
- **M2** Git output is redacted (credentials in URLs, tokens) before it reaches the renderer or the database; push never forces.
- **M1** Renderer isolation: `contextIsolation`, no `nodeIntegration`, `sandbox`, strict Content Security Policy, guarded navigation, and a bridge that exposes only named functions (no generic `invoke`, no `runCommand`).
- **M1** The only route to a child process is a single runner that never uses a shell and caps output and runtime.
